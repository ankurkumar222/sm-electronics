Before You Begin — Two Scripts, Two Steps

There are two separate notebooks. Always run them in this order — never skip Step 1.

ascii — two-step-workflow.txt
   STEP 1 — VALIDATE                        STEP 2 — GENERATE
   ┌───────────────────────────┐            ┌───────────────────────────┐
   │ Moto_InputFiles_          │            │ Billing_Summary_          │
   │ Validator.ipynb           │   ─────▶   │ Generator.ipynb           │
   │                           │  only run  │                           │
   │ checks the raw files for: │  step 2 if │ does the actual           │
   │  • duplicate rows          │  step 1 is │ Target vs Achievement     │
   │  • missing / blank data    │   CLEAN    │ calculation                │
   │  • broken references       │            │                           │
   └───────────────────────────┘            └───────────────────────────┘
         RUN THIS FIRST                            RUN THIS SECOND
Why this order matters

Step 2 trusts the numbers it's given — it does not go looking for duplicate invoices or blank cells in the source files. If dirty data goes in at Step 1, Step 2 will calculate confidently and correctly... on the wrong numbers. Always get a clean bill of health from the Validator first.

  1. Step 1
    Run Moto_InputFiles_Validator.ipynb on this month's targets.xlsx and Billing Report. Read its output — it lists duplicate rows and missing/blank data it found.
  2. Step 2
    Only once you're satisfied the files are clean, run Billing_Summary_Generator.ipynb (everything else in this manual describes this script).
01

The Big Picture

In one sentence: Target = what we planned to sell. Achievement = what we actually billed. The whole script exists to line these two up, per person, honestly.

ascii — pipeline.txt
  ┌──────────────────┐      ┌───────────────────────┐
  │   targets.xlsx    │      │ 21_Aug_Billing_Report │
  │  (WHAT WE WANT)   │      │ (WHAT WE ACTUALLY     │
  │                    │      │  BILLED)               │
  └─────────┬──────────┘      └───────────┬────────────┘
            │                             │
            ▼                             ▼
  ┌───────────────────────────────────────────────────┐
  │             THE NOTEBOOK  (9 steps)                │

                 ┌────────────────────────┐

What's Inside Each Input File

ascii — targets.xlsx
  targets.xlsx   (ONE flat sheet — one row per product line)
  ┌────┬──────────┬─────────────────┬─────┬──────────┬──────────┐
  │ .. │ Currency │ Sales Incharge  │ ... │ Aug_Val  │ Sept_Val │
  ├────┼──────────┼─────────────────┼─────┼──────────┼──────────┤
  │ .. │ INR      │ KULDEEP KUMAR   │ ... │ 500000   │ 510000   │ ← Line business
  │ .. │ USD      │ ARPIT SINGH     │ ... │ 30000    │ 32000    │ ← USD-SG business
  │ .. │ DIRECT   │ HARSH DOSHI     │ ... │ 5000     │ 4800     │ ← USD-Direct business
  └────┴──────────┴─────────────────┴─────┴──────────┴──────────┘
          ↑ this ONE column decides which "bucket" the row's TARGET belongs to
ascii — 21_Aug_Billing_Report.xlsx
  21_Aug_Billing_Report.xlsx   (4 separate sheets)
  ┌──────────┬──────────┬─────────┬───────────────────────┐
  │   Line   │  MOUSER  │   USD   │        Direct          │
  ├──────────┴──────────┴─────────┴───────────────────────┤
  │ each sheet = actual invoices billed this month          │
  │ each has a "salesperson" column + a value column        │
  └────────────────────────────────────────────────────────┘
Key idea

Target comes from one file organised by a Currency column. Achievement comes from another file organised by which sheet a row sits in. The script's whole job is lining these two different organisations up, person by person.

03

Columns We Actually Use — and Why

Both files have 20-50 columns. The script only ever touches a handful. Everything else (SAP numbers, part numbers, zones, quantities, prices…) is ignored — it's not needed for a Target-vs-Achievement report.

From targets.xlsx

ColumnUsed forWhy we need it
Currency Bucketing Tells us which business the row's target belongs to: INR → Line (₹Cr), USD → USD-SG ($M), DIRECT → USD-Direct ($M). Without this column we can't split one flat sheet into three business lines.
Sales Incharge Grouping The salesperson who owns this target. We group-and-sum every row by this column to get "how much is this person's target."
Customer Name JNS carve-out Only checked for one thing: does it contain "JNS"? If yes, that row's target is pulled into the separate JNS-TFT line instead of plain USD-SG (see §06).
<Month>_FY..._Val
e.g. Aug_FY2627_Val		 The number The actual target rupee/dollar figure for the month being reported. The script auto-detects which month's column to read from the Billing Report's own invoice dates — it never has to be told the month by hand.

From the Billing Report (per sheet)

SheetColumnUsed forWhy we need it
Line Basic Value The number The pre-tax billed amount — this is the true "achievement" figure. Not "Total Value" (that includes GST/freight and overstates the real number — see §05).
Line Sales Employee Name Grouping Who billed this invoice — grouped the same way as Sales Incharge in targets.xlsx, after fuzzy name-matching (§07).
Mouser Basic Value The number Same reasoning as Line — pre-tax achievement for Mouser-brand billing.
Mouser Sales Employee Name Grouping Same as above.
USD Row Total in USD The number This sheet has no separate Basic/Total split — this single column is the achievement figure for USD-SG business.
USD Sales Employee Grouping Same grouping role as the Line sheet's salesperson column.
USD Customer Name JNS carve-out Checked for "JNS" — any matching row is moved out of USD-SG into JNS-TFT achievement, mirroring the target-side carve-out.
Direct Row Total in USD The number Achievement figure for USD-Direct business.
Direct Sales Person Grouping Same grouping role (note: this sheet calls the column "Sales Person", not "Sales Employee" — the script looks for both spellings).
All 4 sheets Inv Date / Posting Date / Document Date
(whichever exists)		 Month detection Not part of the money calculation at all — used once, up front, to figure out which month this report is for, so the right target column gets picked automatically.

The Core Calculation

Same shape, every single time, for every business line: filter → group → sum → divide.

ascii — calc-flow.txt
                     TARGET                       ACHIEVEMENT
                (from targets.xlsx)           (from Billing Report)
                       │                               │
                       ▼                               ▼
              ┌─────────────────┐            ┌──────────────────────┐
              │ filter rows by  │            │  filter rows by       │
              │ Currency =      │            │  which SHEET           │
              │ INR/USD/DIRECT  │            │  (Line/USD/Direct)     │
              └────────┬────────┘            └──────────┬─────────────┘
                       │                                 │
                       ▼                                 ▼
              ┌─────────────────┐            ┌──────────────────────┐
              │ group by        │            │  group by              │
              │ Sales Incharge  │            │  Sales Employee/Person  │
              └────────┬────────┘            └──────────┬─────────────┘
                       │                                 │
                       ▼                                 ▼
              ┌─────────────────┐            ┌──────────────────────┐
              │ SUM this month's│            │  SUM Basic Value        │
              │ _Val column     │            │  (not Total Value!)     │
              └────────┬────────┘            └──────────┬─────────────┘
                       │                                 │
                       └────────────┬────────────────────┘
                                    ▼
                          ┌───────────────────┐
                          │  %  =  ACH / TGT   │
                          └───────────────────┘
05

Basic Value vs Total Value

This one column choice was the single biggest source of error before it was fixed.

ascii — why-basic-value.txt
  Total Value  =  Basic Value + GST + Freight + Tax    ← includes extra stuff
  Basic Value  =  the actual pre-tax billing number     ← THIS is what matches
                                                            real reported numbers
How we know

The Billing Report's own printed grand-total row (row 1 of the Line/Mouser sheets) lines up exactly under "Basic Value" — not "Total Value". That's the company's own arithmetic confirming which column is correct.

06

The JNS-TFT Carve-out

One customer — JNS Instruments — sits inside the ordinary USD sheet, but real business practice tracks it as its own line, separate from generic USD-SG.

ascii — jns-carveout.txt
   USD sheet (as it arrives)
   ┌────────────────────────────────────┐
   │ Customer: Acme Corp        → USD-SG │
   │ Customer: JNS INSTRUMENTS  → ???    │  ← treated differently
   │ Customer: Beta Ltd         → USD-SG │     in real business
   └────────────────────────────────────┘
                     │
                     ▼   if Customer Name contains "JNS"
           ┌─────────────────────┐
           │   pulled OUT of      │
           │   USD-SG into its    │
           │   own bucket:        │
           │      "JNS-TFT"        │
           └─────────────────────┘
How we found it

Four identical $107,640 rows for one customer accounted for the entire gap between the raw USD sheet total and the real reported USD-SG figure. Not a guess — a traceable, provable pattern in the data.

07

Fuzzy Name Matching

Real files spell the same person differently across sheets. The script compares every name it finds to every other name and merges the ones that are similar enough — automatically, no maintained list required.

ascii — name-match.txt
   Raw names seen across both files:

   "DHIRENDER PANDEY"   ─┐
                          ├── 92% similar  →  merged into ONE person
   "DHIRENDRA PANDEY"   ─┘

   "SURAJ PANDEY"       ─┐
                          ├── only 40% similar  →  NOT merged (correctly!)
   "DHIRENDER PANDEY"   ─┘

Every merge the script makes is printed on screen each run, so a human can catch a wrong merge before it silently combines two different people's numbers.

09

Hardcoded vs Automatic

Hardcoded — edit Step 1 by hand

  • REPORT_PERSONS — the exact names, spelling, and order shown in the report
  • MOUSER_TARGET_LAKH_DEFAULT (13L guess) — Base File has zero Mouser targets to read
  • MOUSER_TARGET_LAKH_OVERRIDES — Harsh=55, Abhishekh=3 (real confirmed numbers)
  • INCLUDE_JNS_TFT / JNS_CUSTOMER_MATCH — the "JNS" keyword and on/off switch
  • NAME_MATCH_THRESHOLD — the 90% similarity cutoff

Automatic — no edit ever needed

  • Which file is the Base File vs the Billing Report
  • Which month is being reported
  • Salesperson name matching (typos, spelling variants)
  • All Target vs Achievement math
  • Output filename + timestamp
  • Validation / reconciliation checks

11

🚨 When Could This Give a Wrong Answer?

RiskWhy it happensHow you'd notice
Format change Headers reformatted Row 1/2 assumption breaks Script crashes loudly — good, it fails safe instead of guessing.
Name gap Very different spelling / nickname Fuzzy match (90%) doesn't catch it — billing "vanishes" from that person's target Step 8's reconciliation prints a MISMATCH.
Wrong merge Two different people, similar names Fuzzy match wrongly merges them — numbers get combined Step 3b prints every merge — read it each run.
Stale numbers Mouser / JNS figures go out of date These are hand-typed, not computed — nobody updates them No automatic warning — this is a human process gap, not a bug.
Unknown flag The "Sales Changes" reassignment flag 50 rows in targets.xlsx carry a flag we couldn't decode A few people's targets are off by ~1-2% (known, unresolved).
Renamed column A sheet/column gets renamed Fuzzy column matching needs some shared keywords Script crashes, or that category quietly reads as 0.
Skipped Step 1 Validator not run first Duplicate rows or missing data in the source files go unnoticed Generator calculates confidently on bad input — always run Moto_InputFiles_Validator.ipynb first (see §00).

How Validation / Reconciliation Works

Before the final Excel file is saved, the Generator checks its own math two different ways — and refuses to stay quiet if they disagree.

ascii — reconciliation.txt
   WAY 1                                    WAY 2
   Add up every person's                    The raw total already
   achievement, one by one                  printed at the top of the
   (Kuldeep + Arpit + Mahesh + ...)          Billing Report sheet itself
              │                                          │
              └───────────────┬──────────────────────────┘
                               ▼
                     Do these two numbers
                           MATCH?
                       │            │
                     YES            NO
                       │            │
                       ▼            ▼
                 print "OK"    print "MISMATCH"
                                     │
                                     ▼
                     almost always means: a salesperson's
                     name didn't get matched correctly and
                     their billing "fell through the cracks"

Two extra sanity scans, every run

  • Billing with no target — someone billed real money this month but has no target row in targets.xlsx (something's missing on the target side)
  • Way-over-target achievement — anyone whose achievement is wildly above their target (e.g. Arpit's 5608% JNS anomaly) gets flagged for a human look, not hidden inside a big percentage number
Why this matters

This is a built-in second pair of eyes. It catches data problems (a name that didn't match, a missing target row) — not code bugs — before the report reaches the CTO/CXO. "All OK, nothing flagged" is what makes a report trustworthy enough to forward without re-checking it by hand.

13

Monthly Checklist

This automates the math. It does not automate judgment.

  • Step 1 Run Moto_InputFiles_Validator.ipynb on this month's files — check for duplicates and missing data
  • Only once satisfied it's clean — drop the files into input_files/
  • Step 2 Run Billing_Summary_Generator.ipynb — Restart & Run All
  • Read the Step 3b output — any name merge that looks wrong?
  • Read the Step 8 output (§12 above) — any reconciliation MISMATCH or flagged anomaly?
  • If a new joiner or a real Mouser number came in — update the Generator's Step 1 settings first, then re-run
  • Only then forward the file in output_files/ to the CTO/CXO
Bottom line

If the Validator is clean and the Generator's own checks both say "all clear," the numbers are trustworthy — the script did the arithmetic correctly on whatever data it was given. Anything either script flags is exactly where a human still needs to look.

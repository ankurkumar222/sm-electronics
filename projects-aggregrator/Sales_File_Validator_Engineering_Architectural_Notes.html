Yes. Now that I have the actual Sales_File_Validator.ipynb, I would change the previous framework substantially.

2. Rule Category 1 — File Pairing

INT

This happens before Excel-content validation.

INT-002 — Sent/Received File Pairing

Sent Files                         Received Files

Harsh.xlsx        ───────────────► Harsh.xlsx
Arpit.xlsx        ───────────────► Arpit.xlsx
Suraj.xlsx        ───────────────► ❌ Missing
                                          
Unknown.xlsx      ◄─────────────── Returned only

The validator matches files using the salesperson name, rather than requiring the exact filename to be identical. This handles names such as Copy of Harsh-...xlsx.

Rule

INT-002
────────────────────────────────────────
Every sent file must have a return file.
Every return file must have a matching sent file.

Severity

CRITICAL

Why it matters

If there is no pair:

NO SENT FILE
      │
      ▼
Cannot establish baseline
      │
      ▼
       ❌

This is therefore an intake/integration rule, not a spreadsheet-content rule.

3. Rule Category 2 — Structure

STR

This category answers:

"Is the Excel file structurally safe to validate?"

Your actual code has five main structural rules plus one baseline-consistency rule.

STR-001 — Required Sheet Missing

Example:

Expected:

INR Sheet     ✅
USD Sheet     ✅
Direct Sheet  ✅


Returned:

INR Sheet     ✅
USD Sheet     ❌
Direct Sheet  ✅

Result:

STR-001
CRITICAL

The code explicitly raises this when a sheet existed in the sent file but is missing from the return.

STR-002/003 — Header Changed / Moved / Missing

This is actually two structural concepts grouped into one finding code.

The validator compares:

SENT                         RETURNED

Column A = Customer Code     Column A = Customer Code   ✅
Column B = Customer Name     Column B = Part Number     ❌
Column C = Part Number       Column C = Customer Name   ❌

So this catches:

Header changed
Header moved
Header missing
Column position changed

Rule

STR-002/003
────────────────────────────────────────
Every header must remain exactly where
it was in the sent file.

Severity

CRITICAL

And importantly, the code stops processing that sheet after a header break, because column meaning can no longer be trusted.

That's a very good architectural decision.

8. Rule Category 4 — Protected Data

PRT

This is the heart of your original requirement.

The logic is:

              Column changed?
                    │
              ┌─────┴─────┐
              │           │
             NO          YES
              │           │
              ▼           ▼
             ✅      Is it allowed?
                            │
                       ┌────┴────┐
                       │         │
                      YES        NO
                       │         │
                       ▼         ▼
                      ✅        ❌ PRT

The code explicitly follows a default-protected model:

A column has to be explicitly allowed; it is never assumed safe to edit.

This is one of the strongest architectural aspects of the current implementation.

11. What PRT Actually Protects

This is important because the code's architecture is slightly different from our earlier conceptual model.

It doesn't simply say:

Master data = protected
Budget = protected
Forecast = protected

Instead it effectively says:

             EVERY COLUMN
                  │
                  ▼
          Is it derived?
             /       \
           YES       NO
            │         │
            ▼         ▼
       CAL checks   Is allowed?
                       │
                  ┌────┴────┐
                  │         │
                 YES        NO
                  │         │
                  ▼         ▼
                 OK        PRT

So PRT is actually a generic "unauthorized change" rule.

That's a better way to document it.

11.1 PRT in Plain Language — The Simple Rule Behind It

Everything in the file is protected by default. Only a small, explicit list of columns is allowed to change each cycle (this cycle: Nov(F) Qty, Sep(F) Qty, Oct(F) Qty, Oct Incoming, EP Price, Remarks). Everything else falls under Protected Data automatically — nobody had to list out every protected column by name; anything not on the "allowed" list is protected.

What Actually Falls Under It, in Plain Terms

1. Customer & business identity — never touched

  • Customer Code, Customer Name, Currency, Zone/Region
  • Salesperson name, Sales CSR, Principal (brand), Make, PM Names
  • Part Number, Segment/Sub-Segment, End Customer details

Why protected: this is master data pulled from your CRM before the file was ever sent — sales has no reason to ever edit it.

2. This year's official Budget — the whole Apr–Mar row of Quantity columns

  • Apr'26(B) Qty, May'26(B) Qty … all the way through Mar'27(B) Qty

Why protected: this is the approved annual target, set once earlier in the year. It's fixed for the whole year — sales editing it would mean quietly changing the company's official plan.

3. Forecast months that aren't "due" yet this cycle

  • Right now: Dec(F) Qty, Jan(F) Qty, Feb(F) Qty, Mar(F) Qty
  • (Only Nov, Sep, Oct are allowed this cycle — next cycle, the allowed list shifts forward and this list shifts with it)

12. Rule Category 5 — Formula Integrity & Calculation

CAL

This is another area where the actual implementation is more sophisticated than the original assumptions.

Your code treats:

Budget Value
Forecast Value
Summary Formula

as derived categories rather than normal Sales-editable columns.

The principle is:

               DERIVED FIELD
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
     Did value change?    Does formula/
                          calculation work?
          │                   │
          │                   ▼
          │                 CAL-001
          │
          └── NOT the primary test

This is important because a formula-driven Value is expected to change when its inputs change.

So:

"Value changed"

does **not automatically mean:

"Sales changed something they shouldn't."

13. CAL-001 — Calculation Integrity

Example:

Qty = 100
EP Price = ₹50

             │
             ▼

Expected Value
= 100 × ₹50
= ₹5,000

If returned file says:

Value = ₹5,000

✅ CAL-001 passes

But:

Value = ₹50,000

then:

❌ CAL-001

The code also applies a configurable tolerance:

cal_tolerance = 0.01

to accommodate rounding differences.

14. CAL-001 Also Covers Roll-up Calculations

Your validator isn't only checking:

Qty × Price = Value

It also checks summary/roll-up formulas.

Conceptually:

Apr + May + Jun + ... + Nov
                  │
                  ▼
             Roll-up total
                  │
                  ▼
            Expected value
                  │
                  ▼
             Compare actual

So CAL-001 is better described as:

Calculated / derived value does not agree with its source inputs.

That is more accurate than calling it only a "Qty × Price" rule.

15. Rule Category 6 — Change Pattern

PAT

This category asks a different question:

"The change is technically allowed — but is the amount of change suspicious?"

Your current implementation has:

PAT-001 — Excessive Change Volume

Configuration:

pat_suspicious_pct = 50

So if an allowed column changes on ≥50% of applicable rows:

Nov(F) Qty

Total rows       = 1,000
Changed rows     =   600

600 / 1000
     │
     ▼
    60%
     │
     ▼
≥ 50%
     │
     ▼
⚠️ PAT-001

The code deliberately excludes derived categories from this test because their changes are expected to follow their inputs.

18. One Important Architectural Detail

I would not create ALW-001****, ALW-002****, etc. as failure codes in the current implementation.

Why?

Because "allowed" isn't an error.

Your actual architecture is:

                COLUMN
                  │
                  ▼
           classify_header()
                  │
                  ▼
             is_allowed()
                  │
          ┌───────┴────────┐
          │                │
       ALLOWED          NOT ALLOWED
          │                │
          ▼                ▼
     Continue             PRT
     validation           ERROR

So ALW is better treated as a configuration / permission model, not a finding category.

That's an important refinement to the framework.

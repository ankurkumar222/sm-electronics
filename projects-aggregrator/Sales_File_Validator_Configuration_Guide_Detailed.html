1. ⚙️ The Big Picture

Think of CONFIG as the control panel. The validation engine should normally remain unchanged. The configuration tells the engine what business cycle it is validating.

                         CONFIGURATION
                               │
             ┌─────────────────┼─────────────────┐
             ▼                 ▼                 ▼
          FOLDERS          BUSINESS CYCLE     THRESHOLDS
             │                 │                 │
             ▼                 ▼                 ▼
        Where are files?   What may Sales     How sensitive
                           edit this month?   are checks?
Simple rule to remember
Every month, the validator logic should stay the same. The business-cycle configuration moves forward.

For example, if November is the active forecast month this cycle, configure November. When the cycle moves to December, update the month configuration rather than rewriting validation logic.

3. 📅 Active Forecast Month

This is one of the most important settings in the entire validator.

What does “Active Forecast Month” mean?

The spreadsheet contains forecast columns for multiple months. Sales is not expected to actively work on all of them in every cycle.

Active Forecast Month means: “Which forecast month is the main Sales input for this validation cycle?”

Forecast timeline

Apr   May   Jun   Jul   Aug   Sep   Oct   NOV   Dec   Jan   Feb   Mar
 │     │     │     │     │     │     │     │     │     │     │     │
 │     │     │     │     │     │     │     │     │     │     │     │
                                   catch-up   ★ ACTIVE
                                              │
                                              ├── Nov(F) Qty
                                              └── Nov(F) Value

For the current example:

ACTIVE_FORECAST_MONTH = "Nov"
What does the validator do with this setting?

The validator uses the active month to decide which forecast fields are expected to be editable.

                 ACTIVE_FORECAST_MONTH
                         │
                         ▼
                      "Nov"
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
          Nov(F) Qty           Nov(F) Value
              │                     │
              └──────────┬──────────┘
                         ▼
                    Sales input

If November is active, a change in November forecast fields can be legitimate. A change in an unrelated future forecast month can instead become a protected-data violation.

Why is this configuration necessary?

Without this setting, the validator cannot distinguish between:

"Sales updated the forecast month they were asked to work on"
                         VS
"Sales changed a forecast month that was not due yet"

That distinction is central to the validation model.

What happens if I configure the wrong month?
Wrong active month = potentially wrong validation results.

Example: suppose November is actually the active month, but configuration says December.

Actual business cycle:
Nov(F) Qty → allowed

Validator configuration:
Dec(F) Qty → allowed

Result:
Nov changes may be incorrectly flagged
Dec changes may incorrectly be accepted

So this setting must be checked before every monthly run.

What should I change next month?
November cycle:
ACTIVE_FORECAST_MONTH = "Nov"

December cycle:
ACTIVE_FORECAST_MONTH = "Dec"

January cycle:
ACTIVE_FORECAST_MONTH = "Jan"
Change the configuration, not the validation engine.

4. 🔄 Catch-up Months

Catch-up months are previous forecast months that Sales is still allowed to correct or fine-tune.

What is a catch-up month?

Imagine November is the main forecast month. September and October are already behind us, but Sales may still need to correct those forecasts using information that became available later.

                     MAIN WORK
                         │
                         ▼
Sep          Oct          NOV          Dec
│            │             │            │
│            │             │            │
└─ catch-up ─┘             ★ active     🔒
   corrections

So catch-up does not mean “Sales can edit everything in those months.” It means the configured forecast fields for those months are treated as legitimate editable inputs according to the validator's rules.

Current example configuration
CATCHUP_FORECAST_MONTHS = ["Sep", "Oct"]
Sep(F) Qty     → ✅ allowed catch-up
Oct(F) Qty     → ✅ allowed catch-up
Nov(F) Qty     → ✅ active month

Dec(F)         → 🔒 protected
Jan(F)         → 🔒 protected
Feb(F)         → 🔒 protected
Mar(F)         → 🔒 protected
Why do we need this separate from the active month?

Because the business process has two different kinds of legitimate changes:

Active monthThe main forecast Sales is currently expected to fill.
Catch-up monthsPrevious months where Sales may still make corrections.

This gives the validator a more precise rule than simply saying “Sales can edit forecast columns.”

What happens if catch-up months are wrong?
If Oct should be editable but Oct is NOT configured:

Oct(F) change
      ↓
Validator sees it as protected
      ↓
❌ False violation
If Dec should be protected but Dec is accidentally configured
as a catch-up month:

Dec(F) change
      ↓
Validator may accept it
      ↓
⚠ Real unauthorized change could be missed
Therefore, catch-up configuration should be based on the actual monthly business process, not simply on the previous two calendar months.
What should I review each month?

Ask one simple question:

“Which previous forecast months are Sales still officially allowed to correct this cycle?”

Put exactly those months in CATCHUP_FORECAST_MONTHS.

5. 🚚 Active Incoming Month

Incoming represents shipment/incoming information. The validator treats one configured recent Incoming month as the active Sales-editable month.

What does “Active Incoming Month” mean?

It means:

“Which month's Incoming column is Sales currently allowed to update?”
ACTIVE_INCOMING_MONTH = "Oct"
Incoming

Aug ──🔒
Sep ──🔒
Oct ──✅  ← Active Incoming month
Nov ──🔒
Dec ──🔒
Why is Incoming treated separately from Forecast?

Forecast and Incoming represent different business concepts.

AreaMeaning
ForecastWhat Sales expects / forecasts.
IncomingShipment or goods-in-transit information that may change as delivery status becomes clearer.

Therefore the validator needs separate configuration for the active Forecast month and active Incoming month.

Example of a legitimate Incoming change
Before:
Oct Incoming = 500

New shipment information arrives:
300 units will actually arrive this month

After:
Oct Incoming = 300

                         ↓
                    Allowed change

The exact business reason may vary, but the important point is that the configured active Incoming month is considered an editable Sales input.

What if the wrong Incoming month is configured?
Actual:
Oct Incoming is active

Configuration:
Nov Incoming is active

Then:
Oct Incoming change → may be incorrectly flagged
Nov Incoming change → may be incorrectly accepted
Always verify this setting against the current business cycle.

Why this example matters

The validator is not simply asking:

“Did anything change?”

It is asking:

“Did anything change?

That is the core business logic of the solution.

7. ⭐ Recommended CONFIG Structure

Keep configuration separate from validation logic. This makes the notebook easier to operate and prevents monthly business changes from becoming code changes.

Recommended configuration layout
# ============================================================
# 1. FILE CONFIGURATION
# ============================================================

SENT_DIR = "input_files/sent_files"
RECEIVED_DIR = "input_files/received_files"
REPORT_DIR = "validation_reports"


# ============================================================
# 2. BUSINESS CYCLE CONFIGURATION
# ============================================================

ACTIVE_FORECAST_MONTH = "Nov"

CATCHUP_FORECAST_MONTHS = [
    "Sep",
    "Oct"
]

ACTIVE_INCOMING_MONTH = "Oct"


# ============================================================
# 3. VALIDATION SENSITIVITY
# ============================================================

PAT_SUSPICIOUS_PCT = 50

CAL_TOLERANCE = 0.01
Section 1 — File Configuration
SettingQuestion it answers
SENT_DIRWhere are the original files?
RECEIVED_DIRWhere are the returned Sales files?
REPORT_DIRWhere should validation results be written?

These normally do not change from month to month if the folder structure stays the same.

Section 2 — Business Cycle Configuration
SettingQuestion it answers
ACTIVE_FORECAST_MONTHWhich forecast month is the main active month?
CATCHUP_FORECAST_MONTHSWhich previous forecast months may still be corrected?
ACTIVE_INCOMING_MONTHWhich Incoming month may Sales update?
This is the section you are most likely to update every month.
Section 3 — Validation Sensitivity
SettingQuestion it answers
PAT_SUSPICIOUS_PCTAt what percentage of changed rows should an allowed change pattern become suspicious?
CAL_TOLERANCEHow much numerical difference can be ignored as rounding/calculation noise?

These are generally stable settings. They should be changed only when the validation policy changes.

Why not hard-code protected columns?
                    COLUMN
                       │
                       ▼
              Explicitly allowed?
                  /                        YES         NO
                 │           │
                 ▼           ▼
              ALLOW       PROTECT
Default-deny is safer: if a new column appears and nobody has explicitly said Sales may edit it, it is not automatically trusted.
What should never be mixed into monthly configuration?

Avoid putting actual validation algorithms inside the monthly settings.

GOOD:
ACTIVE_FORECAST_MONTH = "Nov"

BAD:
if month == "Nov":
    special_validation_logic...

The first approach keeps the engine reusable. The second approach gradually turns the validator into a collection of month-specific exceptions.

8. ✅ Pre-Run Checklist

This checklist is designed to be followed immediately before running the notebook.

Step 1 — Check the input folders
1
Open sent_files and confirm the original files sent to Sales are present.
2
Open received_files and confirm the returned Sales files are present.
3
Make sure you are not accidentally mixing files from an older cycle.
sent_files/
    ├── Harsh.xlsx
    ├── Arpit.xlsx
    └── Suraj.xlsx

received_files/
    ├── Harsh.xlsx
    ├── Arpit.xlsx
    └── Suraj.xlsx
Important: The sent file is the baseline. Do not overwrite it with the returned version.
Step 2 — Check the active forecast month

Ask:

“What forecast month is Sales officially working on in this cycle?”

Then verify:

ACTIVE_FORECAST_MONTH = "Nov"

Do not guess based only on today's calendar month. Use the actual business process.

Step 3 — Check the catch-up months

Ask:

“Which previous forecast months can Sales still correct?”

Verify:

CATCHUP_FORECAST_MONTHS = ["Sep", "Oct"]

Check that these are the actual business-approved catch-up months for the cycle.

Step 4 — Check the active Incoming month

Ask:

“Which Incoming month can Sales update right now?”

Verify:

ACTIVE_INCOMING_MONTH = "Oct"
Step 5 — Check sensitivity settings

Normally these remain unchanged:

PAT_SUSPICIOUS_PCT = 50
CAL_TOLERANCE = 0.01

Change them only if the validation policy has been deliberately changed.

Step 6 — Check the file structure before running

Quickly verify:

  • Files are Excel files expected by the validator.
  • Original sent files are not modified.
  • Returned files are the correct cycle.
  • Required sheets are present where expected.
  • No temporary or unrelated files are mixed into the input directories.

10. 🎯 Golden Rules for Operators

The five rules to remember
  1. Never modify the sent baseline file.
  2. Always configure the actual active forecast month.
  3. Only include business-approved catch-up months.
  4. Configure the correct active Incoming month separately.
  5. Do not change validator logic just because the month changed. Update configuration instead.
One-line mental model: “Tell the validator what month Sales is working on, what previous months they can correct, what Incoming month is active, and where the files are.”
